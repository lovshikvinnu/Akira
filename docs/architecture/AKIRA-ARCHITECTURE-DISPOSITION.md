### Evidence labels

Every claim below carries one of four labels. They are never mixed in one statement.

| Label         | Meaning                                                                                                                                            |
| ------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| **FACT**      | Verified directly in the repository at `e58020f`. Cited as `path:line` (relative to `src/` unless it starts with `tests/`, `scripts/` or `docs/`). |
| **AUDIT**     | Stated in the architecture audit PDF. Not re-asserted unless it is also marked FACT.                                                               |
| **INFERENCE** | An architectural conclusion drawn from FACTs.                                                                                                      |
| **PROPOSAL**  | A recommendation for the future architecture.                                                                                                      |

In tables, the _Current role / Reachability / Actual behaviour_ columns are FACT. The _Disposition / Future role / Reason_ columns are PROPOSAL unless they say otherwise.

Reachability vocabulary:

| Term              | Meaning                                                                         |
| ----------------- | ------------------------------------------------------------------------------- |
| **live**          | Reached from a production entry point and has an effect that something consumes |
| **inert**         | Reached and executed, but produces nothing that any consumer reads              |
| **loaded-unused** | Evaluated at runtime because a barrel imports it, but no symbol is ever called  |
| **unreachable**   | No production importer at all                                                   |
| **partial**       | Some entry points are live, others are never called                             |

## 1. Purpose

AKIRA is heading toward this architecture:

```
External AI agents → MCP → AKIRA → VAJRA → { GENESIS (cognition), OS (domain), HANDS (execution) }
```

Phase 0 decides, for every significant part of the **current** system, whether it survives into that architecture, and in what form:

| Disposition | Meaning                                                     |
| ----------- | ----------------------------------------------------------- |
| KEEP        | Survives as it is                                           |
| REFACTOR    | Survives, but its boundary, ownership or lifecycle changes  |
| MERGE       | Converges with overlapping parts into one canonical concept |
| KILL        | Removed                                                     |
| LATER       | Deliberately not addressed before MCP                       |

It also names the prerequisites that must be true before MCP can safely become an external interface, and the work that must **not** be pulled in ahead of MCP.

Phase 0 does not design MCP, VAJRA or HANDS. It does not fix anything either. Defects found during the investigation are recorded in [Appendix B](#appendix-b--defects-found-documented-not-fixed).

### 2.2 Snapshot facts

- **FACT. Cognition runs in the browser.**
  - `__root.tsx:18-23` imports `@/genesis`, whose barrel composes the pipeline at module scope (`genesis/index.ts:160-162` → `composition.ts:120`).
  - The model call is a browser `fetch` (`genesis/context/ai/providers/gemini-provider.ts:164,311`, `openrouter-provider.ts:156,292`).
- **FACT. A server-side GENESIS instance also exists.** This resolves the audit's UNKNOWN #2.
  - `composition.ts` has no `window` guard, and its own comment says one attachment "serves browser and server alike" (`composition.ts:100-103`).
  - SSR imports `__root` (`routeTree.gen.ts:11`), and `persistPublishEvent` republishes every non-transient client event onto the server bus (`instrumentation/server/index.ts:63-64`).
  - On the server `hydrated` is never set, so `saveMemory` updates in-memory state and never writes to disk (`persistence/akira-store.ts:1359`).
  - Not verified: whether SSR and the server-function handlers share module instances at runtime. That is a bundler property.
- **FACT. The database is the only durable layer.**
  - The workspace is stored as rows.
  - Cognition is stored as one JSON event stream (`settings.genesis_memories`), rewritten whole on each change (`akira-os/settings/server/index.ts:46-50`) and replayed into memory at boot (`__root.tsx:242`) and on every New Chat (`chat.tsx:591-592` → `genesis/context/state/service.ts:45`).
- **FACT. The model is a text service.**
  - No output is parsed for actions.
  - `finishReason: "tool_calls"` is typed (`genesis/context/ai/types.ts:22`), but no adapter produces it and nothing reads it.
- **FACT. AKIRA has no mission object, command router, mission manager or workflow engine.** This confirms the audit.
  - The "Daily Mission" route only redirects to `/tasks` (`routes/daily-mission.tsx:3-10`).
  - `CommandPalette` is a UI search and navigation panel, not a command bus (`app/shell/CommandPalette.tsx`).

## 4. GENESIS Disposition

**FACT. How GENESIS boots.**

- Importing `@/genesis` composes the system: `genesis/index.ts:160-162` → `composition.ts:120-131`.
- Composition runs 12 processors, each in its own try/catch, in this declared order (`composition.ts:67-105`):
  1. chatDeclarationPromoter
  2. candidateService
  3. validationEngine
  4. relationshipEngine
  5. storyBuilder
  6. importanceBuilder
  7. identityBuilder
  8. understandingEngine
  9. insightEngine
  10. contextBuilder
  11. retentionService
  12. realityAdapter
- Six of those processors already subscribe themselves when their module loads, before composition runs. So the declared order is not the real subscription order. The six:
  - `candidate-service.ts:109`
  - `memory/relationships/relationship-service.ts:339`
  - `understanding/engine.ts:189`
  - `understanding/identity-builder.ts:155`
  - `insights/insight-engine.ts:173`
  - `context/context-builder.ts:122`

**FACT. What is outside composition.** Recall and the session/context engines are not composed. `companionStateService` and `__root.tsx` start them.

**FACT. No engine calls a model.** The only model calls are in `context/ai/providers`.

**INFERENCE.** AKIRA has two identity stores. They have different lifetimes (one cleared on replay, one never), different matching rules, and different persistence (none, versus events that are written but never read back). An external `identity.read` that picks either one would give an answer that depends on boot history. This is why the identity merge is a pre-MCP _ownership_ question (§13) and not just cleanup.

## 5. Runtime Disposition

### 5.1 Reachability (FACT)

- No file outside `src/runtime`, `src/sdk`, `src/compatibility` and `src/analytics` imports them, whether statically, dynamically or through `require`.
- The only cross-references are among the four directories themselves. For example, `compatibility/core/compatibility-factory.ts:10` imports `sdk/core/sdk-context`.
- Tests that import them:
  - runtime: `tests/runtime.test.ts`, `capability-registry.test.ts`, `lifecycle.test.ts`, `manifest.test.ts`, `dependency-resolver.test.ts`
  - SDK: `tests/sdk/akira-sdk.test.ts`
  - analytics: `src/analytics/tests/analytics.test.ts`
  - compatibility: **no test at all**
- No production code constructs `RuntimeManager` or `CapabilityRegistry`. No module manifest file (`manifest.yaml/.yml/.json`) exists anywhere, although the runtime looks for one (`runtime-manager.ts:219-223`).
- **The runtime's event bus is the legacy string-topic bus** (`shared/infrastructure/event-bus/index.ts:24-78`). It has no connection to `globalEventBus`, so even a wired runtime module would never see a platform event (`runtime-manager.ts:448-451`).
- `RuntimeManager` imports `fs` and `path`, which makes it Node-only.
- `PermissionManager` is constructed (`runtime-manager.ts:47`) and never consulted.
- The SDK's required permission IDs (`events.publish`, `timeline.query`, and others) **do not exist** in `permission-catalog.ts:9-144`. Wiring the two together would throw `PermissionNotFoundError`.
- Every SDK wrapper rethrows any error as `PermissionRequiredError` (for example `sdk/events/event-api.ts:12-16`).
- `analytics/service/analytics-service.ts:368` creates a singleton at module scope that opens the DB on import.
- ADR status lines:
  - ADR-011/012/013: "Proposed / Accepted"
  - ADR-014: does not exist
  - ADR-015 through ADR-021: Accepted
  - ADR-022: Accepted, supersedes parts of ADR-021, and is stale about persistence health not being wired (`akira-store.ts:216,228-229` now writes the health registry)

**Duplicated or misplaced responsibilities (INFERENCE):**

1. **Memory replay has three triggers.** O1 (`__root.tsx:242`), O6 at boot, and O6 on every New Chat. At boot, replay runs twice: once against an empty stream, which is a no-op, and once after hydration.
2. **Lifecycle of the memory layer is owned twice.** O3 composes `validationEngine` and O6 disposes it.
3. **Boot ordering is split.** It lives across a React route (O1/O2), import side effects (O3/O4/O14/O15) and the first RPC (O10).
4. **Conversation orchestration lives in the UI** (O11), and so does session creation (O12).
5. **Nothing coordinates across systems.** This matches the audit: no component holds cross-system command authority.

**PROPOSAL.** One explicit lifecycle owner, outside the UI and outside GENESIS, that runs boot, hydration, cognition start, replay and shutdown, in order and once. This is the seed that VAJRA later absorbs. It is a Phase 5 item, but the decision of _where it lives_ is a Phase 1 prerequisite (§13).

### 9.2 Sessions (FACT)

**PROPOSAL.**

- **Remain separate, but be renamed.** Only _work session_ and _conversation_ are domain entities. They should be the only things called "session" and "conversation" in any public capability.
- **Companion session → lifecycle.** It is a cognition-lifecycle concept and moves under the lifecycle owner.
- **Internal only:** recall session and presence type.
- **UI-local:** the boot flag.

### 9.3 Memory

**FACT.** There are three owners (runtime, durable stream and policy). There is also a separate, non-memory past-conversation archive used by Historical Recall.

**PROPOSAL.**

- **GENESIS owns memory end to end.** Persistence provides storage only.
- **The conversation archive stays separate.** It is OS-domain data that cognition may _read_. It is not memory.

### 9.4 Events

**FACT.** There are three event vocabularies:

- platform `AkiraEvent` on M1;
- cognition `MemoryEvent` via `eventService`;
- `identity.*` and `planning.*` constants that live in `contracts/events.ts` but are never published on the bus.

Durability is chosen by event type. As a result, wrong event types are used as a durability lever:

- "Companion Session Ended" is recorded as `note_edited` (`chat.tsx:852`).
- `correctState` records `note_created` (`state/service.ts:121`).

**PROPOSAL.**

- **Split the vocabulary in two.** Domain events (what happened in the workspace) and cognition events (what GENESIS recorded).
- **Make durability explicit**, not inferred from the type name.
- **Exclude system bookkeeping** (`identity.*`) from the user-history budget. Phase 2.

### 9.5 Lifecycle and orchestration

See §8. **MERGE.** The responsibilities spread across O1, O2, O3, O4, O6, O10 and O14 converge on a single lifecycle owner. `src/runtime`'s `LifecycleManager` is a pattern donor (LATER), not the implementation.

### 9.6 Context

**FACT.** Three overlapping situational models are live:

- the ContextPackage (`contextBuilder`);
- the ResolvedContext (`contextResolutionService`);
- the CompanionState.

There is also an unreachable duplicate chain: `context/assembly`, `context/relevance` and `context/intelligence`.

**PROPOSAL.**

- **Keep the three live models.** They are distinct layers: what is remembered, what the situation is, and what the focus is.
- **Expose one read model** that combines them, as `context.read`.
- **MERGE the unreachable duplicates** into the live ones.

### 9.7 Identity

Emergent identity and foundation identity: **MERGE** (§4.3).

### 9.8 Habits and relationships

**FACT. Habits:** observed habits (`habitService`), declared habits (`IdentityHabit`) and `habitRule` (inert).

**FACT. Relationships:** contacts (`relationshipService`), memory links (`memoryRelationshipService`) and `IdentityRelationshipService` (unreachable). Two services share the export name `relationshipService` (`genesis/index.ts:7,72`).

**PROPOSAL.** **LATER**, apart from the naming. These overlaps do not block MCP if they are not exposed.

### 9.9 Configuration and state

**FACT.** Configuration is split across three stores (§6). The open chat and the archive form two chat stores.

**PROPOSAL.** **MERGE** the two chat stores into the conversations module, pre-MCP. Configuration consolidation can wait, but secret exposure cannot (§13).

### 9.10 Duplicate code (FACT)

These files are byte-identical copies with zero importers. The `lib/*` copies are the live ones.

- `src/shared/error/{error-capture,error-page,lovable-error-reporting}.ts`
- `src/shared/utilities/utils.ts`

The two loggers are byte-identical, and so are `executeRequest` and `executeRequestStream`.

**PROPOSAL.** KILL the `shared/` duplicates and MERGE the loggers.

## 13. What Must Be Fixed Before MCP

These are architectural prerequisites, kept to a minimum. Each blocks a safe external interface.

1. **Decide where the authoritative runtime lives (human decision).**
   - Cognition and the model call run in the browser (§2). An MCP server is a server-side process, so it cannot reach browser GENESIS.
   - Choose one:
     - (a) MCP v0 exposes only OS-domain capabilities served from SQLite, plus cognition reads that have a server-side home; or
     - (b) cognition moves server-side.
   - Every later item depends on this choice.
2. **Remove the accidental server-side GENESIS** (#52). Otherwise an MCP server process would contain an unhydrated, accumulating cognition copy that looks like the real one.
3. **One server-side owner per exposed entity, and one write path.** A write that does not come from the browser store must still reach the client cache, the platform event stream and GENESIS. Today only the client store publishes workspace events, so an MCP write would be invisible to cognition (§7).
4. **Move the conversation archive out of `chat.tsx` into the conversations module, and merge the two chat stores** (#3, #16). A route cannot own data that a capability reads.
5. **Give the durable memory stream a single owner.** GENESIS writes it through a contract; persistence stops importing `retention/policy` (#64, #67). Without this, `memory.*` has no well-defined source.
6. **Single owner for cognition lifecycle and replay.** Replay must not be triggered by a route, by `companionStateService` and by New Chat. `closeSession` must not switch off memory promotion (#4, #59, #76). An external reader would otherwise observe a pipeline that is sometimes off.
7. **Merge identity into one store with one lifetime**, and stop cold-boot re-recording of `identity.*` into the user-history budget (#69, #73, #74). Required before `identity.read`.
8. **Define canonical Goal ownership** (definition and owner only, not behaviour). Required before any `goal.*` read. Otherwise defer goal capabilities from v0.
9. **Split the event vocabulary into domain events and cognition events, with explicit durability** (#35). Stop using `note_created` and `note_edited` as durability levers.
10. **Introduce a capability catalogue** (name, read/write class, input and output schema, owner) that is decoupled from server-function names (§11). Add runtime input validation at that boundary.
11. **Add an authorization boundary and close secret exposure.**
    - No generic key-value read or write.
    - Keys are not readable by RPC.
    - No `VITE_*` keys in the bundle.
    - Destructive operations (`reset`, `permanentDelete`) and event injection (`persistPublishEvent`) are unreachable from the capability layer.
12. **A uniform Result/failure contract at the capability boundary.** Today `persist` swallows failures and leaves memory and disk diverged, with no signal to the caller.
13. **Fix the data-integrity defects on paths that will be exposed** (Appendix B: B1, B2, B5, B6, B7, B8, B9). An external agent will hit them deterministically.

## 14. What Must NOT Be Fixed Before MCP

This work is deliberately deferred to prevent scope creep.

- **No VAJRA-era behaviour.** That means planning, reasoning and decision (#90-92); initiative and proactivity (#80); reflection (#81); hypotheses and onboarding (#71); any Mission object, mission manager or workflow engine.
- **Runtime stack.** Do not activate `src/runtime`, `LifecycleManager`, `CapabilityRegistry`, `DependencyResolver` or the permission catalog. Do not build MCP on the SDK.
- **HANDS and execution.** No tool calling, no parsing of model output into actions, no executor, no verification.
- **Analytics** (#49) and the `events` table reader (#30).
- **Observability surfacing** beyond what the Result contract needs. No health UI, tracing or diagnostics (#41).
- **Cognition quality.** Classifier substring matching, aviation-only goal alignment, dead understanding rules, story status semantics, habit decay, the contacts role filter, Historical Recall ranking.
- **Storage format.** Moving `genesis_memories` from a JSON blob to rows. Ownership is pre-MCP; format is not.
- **Unreached identity services** (skills, personality, relationships, update and archive paths) (#75).
- **Model infrastructure.** Multi-provider fallback, retries, local LLMs, model configurability, and moving model calls server-side. The latter is required only if decision 13.1 chooses option (b).
- **Cleanup.** Deleting the KILL items, including the runtime/SDK/compatibility and duplicate files. They are inert, so this can run any time. It must not be bundled into ownership PRs.
- **UI.** No redesign. The Brain Inspector (#5) stays as a dev tool.
- **Legacy migration removal** (#26).
- **Schema runner and numbered migrations** (#23) beyond making schema ownership single.

   ↓

   ↓
