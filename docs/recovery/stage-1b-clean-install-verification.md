# Stage 1B — Clean Installation Verification

**Question under test:** can a developer obtain the repository, install dependencies, and build AKIRA without relying on hidden local state?

**Method:** two independent isolated environments were built in a temporary directory. Nothing was deleted from the development machine, and the user's real database (`%APPDATA%\AKIRA\akira.db`) was never opened for writing — its mtime is unchanged at `Jul 25 21:23`.

| Environment | Source | Purpose |
| :--- | :--- | :--- |
| **E1 — `clean-head`** | `git clone` of committed `HEAD` (`b561730`) | What a developer actually receives today |
| **E2 — `clean-worktree`** | Copy of the working tree, excluding `node_modules`, `.output`, `.tanstack`, `.wrangler`, `.lovable`, `.git` | Whether the Stage 1A recovery is itself reproducible |

**Toolchain used:** Node `v24.18.0`, npm `11.16.0`, Windows 10.0.26200 (MINGW64 shell).

## 2. Hidden Dependency Audit

### 2.1 🔴 CRITICAL — the Stage 1A repair is not committed

**This is the most important finding of Phase 2.**

```
$ git status --porcelain src | grep "^??"
?? src/compatibility/adapters/event-adapter.ts
?? src/genesis/planning/health/createHealthRuleEngine.ts
?? src/genesis/planning/health/rules/HealthyRule.ts
```

All three files created during Stage 1A build recovery are **untracked**. Verified against E1:

```
$ cd clean-head && git log --oneline -1
b561730 audit
$ ls src/genesis/planning/health/createHealthRuleEngine.ts   → MISSING
$ ls src/genesis/planning/health/rules/HealthyRule.ts        → MISSING
$ ls src/compatibility/adapters/event-adapter.ts             → MISSING
```

Consequence, measured in E1 (§4): **a clean clone of committed `main` reproduces the original P0 exactly** — 103 TypeScript errors and `vite build` exit 1 with the same `[UNRESOLVED_IMPORT] '../health/createHealthRuleEngine'`.

Classification: **UNCOMMITTED GENERATED FILE** (more precisely, uncommitted *repair*). The working development machine builds; the repository does not.

### 2.2 🟠 Machine-specific paths in tracked documentation

`README.md` contains 25 cross-reference links of the form:
```markdown
[Architecture Blueprint](file:///C:/Users/lovsh/Desktop/Project%20Akira%20Master/AKIRA/ARCHITECTURE.md)
```
plus screenshot placeholders pointing at `C:/Users/lovsh/Desktop/.../docs/assets/dashboard.png` (a directory that does not exist). These are broken for every other developer and on GitHub. `CONTRIBUTING.md` §6 mandates this convention explicitly. Non-blocking for install, but it is literal "works on my machine" state in version control.

### 2.3 🟡 Test artefacts committed into the source tree

### 2.4 ✅ Native module — checked, and it works

`npm ci` emits a warning that reads like a failure:
```
npm warn allow-scripts 1 package has install scripts not yet covered by allowScripts:
npm warn allow-scripts   better-sqlite3@12.11.1 (install: prebuild-install || node-gyp rebuild --release)
npm warn allow-scripts   Run `npm approve-scripts --allow-scripts-pending` to review...
```
Verified explicitly rather than assumed:
```
$ find node_modules/better-sqlite3 -name "*.node"
node_modules/better-sqlite3/build/Release/better_sqlite3.node
$ node -e "const D=require('better-sqlite3'); new D(':memory:').exec('CREATE TABLE t(a)')"
LOAD OK — sqlite works
```
**The binding is present and functional after a plain `npm ci`.** The warning is advisory (npm 11 script-allowlisting policy), not a build failure. No `node-gyp`, Python, or C++ toolchain was needed. Recorded so this is not mistaken for a blocker.

### 2.5 🟡 Undocumented default: a fresh install writes to the user's real database

`getDatabasePath()` falls back to `%APPDATA%\AKIRA\akira.db` when `AKIRA_DATABASE_PATH` is unset. So running the app — **or the test suite, or `validate:architecture`** — on a machine that already has AKIRA data will target that live database unless the variable is set.

Evidence this has already happened: the live `akira.db` contains an `events` row with `id: "evt-async-1"`, `source: "tasto-test"` *(sic — `tasks-test`)*, a hard-coded test fixture (Phase B §4.8). A test run reached production data at some point.

This verification therefore set `AKIRA_DATABASE_PATH` and `AKIRA_VAULT_PATH` to isolated temporary paths throughout. Classification: **UNDOCUMENTED ENVIRONMENT REQUIREMENT** — not an install blocker, but a genuine data-safety gap with no `.env.example` to warn about it.

### 4.2 Production build produces a Cloudflare worker, not a Node server

```
$ NODE_ENV=production node .output/server/index.mjs
$ echo $?
0                      ← exits immediately, no listener, no output
```

`.output/server/index.mjs` begins:
```js
globalThis.__nitro_main__ = import.meta.url;
...
var services = { ["ssr"]: lazyService(() => import("./_ssr/ssr.mjs")) };
globalThis.__nitro_vite_envs__ = services;
```
It exports a `fetch` handler for a worker runtime. This matches `vite.config.ts`'s own comment: *"nitro (build-only using **cloudflare as a default target**)"*.

**This is configuration, not a defect** — but it has a real consequence: **the production build artefact cannot be self-hosted with `node .output/server/index.mjs`.** For a product described as "desktop-first, offline-first" with a local SQLite database, a Cloudflare Workers target is an odd default (Workers cannot load `better-sqlite3` native bindings at all). No repository documentation mentions how to run a production build, and `npm run preview` is untested here. Recorded as a **BUILD CONFIGURATION** observation for architecture review, not as a Stage 1B blocker — the documented startup path (`npm run dev`) works.

### 4.3 Database initialization — verified from scratch

A brand-new database was created at the isolated path on the first SSR request:

```
akira-test.db      4,096 b
akira-test.db-shm 32,768 b
akira-test.db-wal 259,592 b
```

Contents of the freshly initialised schema:

| Aspect | Value |
| :--- | :--- |
| Tables | **20** — `projects`, `tasks`, `notes`, `sessions`, `settings`, `schema_version`, `migration_history`, `timeline_events`, `search_history`, `fts_workspace` (+5 FTS shadow tables), `vault_files`, `vault_folders`, `vault_tags`, `vault_file_tags`, `vault_file_links` |
| Triggers | **24** |
| Indexes | **38** |
| `schema_version` | `[{ version: 1, applied_at: "2026-09-02T18:03:46.778Z" }]` |
| Row counts | all entity tables **0** — no seed data, no leakage from the dev machine |

**Migration behaviour:** `initializeDatabase()` detected no `schema_version` table, executed `schema.sql` inside a transaction, seeded version 1, then ran the three feature-detection blocks (`timeline_events`, `search_history` + FTS, vault tables). Log confirms: `SQLite Database initialized successfully with schema version 1.` WAL mode active.

**One finding:** the **`events` table does not exist after startup.**
```
$ node -e "... SELECT COUNT(*) FROM events"
events table STILL MISSING (created lazily on first publish)
```
`runEventStoreMigration` runs only when `SqliteEventRepository` is constructed, which happens inside the `persistPublishEvent` RPC handler. So a fresh AKIRA install has **no Event Store until the first event is published** — it is absent from `schema.sql` and from every dynamic-migration block in `initializer.ts`. This is consistent with, and independently corroborates, Phase B §4.8 (the instrumentation pipeline has never been exercised). Non-blocking, but it means the Event Store is not part of the initialised schema contract.

## 6. Reproducibility Verdict

# REQUIRES REMEDIATION

**Basis:** the recovered *source* is fully reproducible — E2 reproduced the development machine's results exactly (9 type errors, 327 tests passing, build exit 0, working startup) from a clean copy with a fresh dependency install and no local state. That is a genuinely good result: there are no hidden generated sources, no global packages, no required secrets, and no undocumented steps needed to build.

**But the *repository* is not reproducible**, because the repository does not contain the recovery. A developer cloning `main` today gets 103 type errors and a failed build (E1). Reproducibility is defined by what is committed, not by what exists on this machine.

The remediation is one command — `git add` the three Stage 1A files — after which this verdict becomes **REPRODUCIBLE WITH DOCUMENTED REQUIREMENTS**, the documented requirements being:

1. Node ≥ 18 (verified on 24.18.0); install with `npm ci`
2. `AKIRA_DATABASE_PATH` should be set for any test or verification run, to avoid writing to live user data (§2.5)
3. No secrets are required; `VITE_*` AI keys are optional and should be left unset unless intentionally shipping them into the client bundle
4. Startup is `npm run dev`; the production build artefact currently targets Cloudflare Workers and is not self-hostable (F2)

I have not run `git add` — committing is your decision, and Stage 1A's holds (`src/diagnostics/`, the event-contract duplicate) are still open pending the architecture decisions escalated in `stage-1b-diagnostics-investigation.md` §7.
