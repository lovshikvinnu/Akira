# ADR-010: Instrumentation Reliability

## Status
Proposed / Accepted

## Context
As the central event framework of AKIRA OS, the Instrumentation subsystem must serve as the permanent, reliable nervous system of the platform. Any failures, bottlenecks, message losses, or out-of-order deliveries in this pipeline would lead to corrupt user timelines, lost analytics insights, or inconsistent companion behavior (GENESIS). We need to document and enforce design decisions surrounding event validation, chronological sequencing, duplicate handling, subscriber boundary failures, and high-performance throughput.

## Decision
We enforce the following stability and performance principles across the entire Event Subsystem:

### 1. Serialization & Validation Strategy
- Only JSON-compatible payloads are accepted.
- Any non-JSON types (such as functions, symbols, circular references, Maps, Sets, Promises, or custom class instances) are rejected at the publisher middleware boundary.
- Middleware validations run synchronously before events enter the Event Bus, guaranteeing that invalid events never touch subscribers or get persisted.

### 2. Event Ordering Guarantees
- Event processing order must follow publication order strictly.
- The Event Store persists events sequentially within transaction scopes.
- The Timeline Subscriber maps events and stores them inside the Timeline DB in their exact order of publishing.
- The Event Bus handles event distribution synchronously per publisher invocation to prevent race conditions during async delays.

### 3. Uniqueness and Idempotency
- Every event is assigned a globally unique UUID `id` generated by the middleware pipeline.
- Both the SQLite Event Store (`events` table) and Timeline (`timeline_events` table) use the immutable event `id` as the primary key.
- Duplicated publish calls (re-publishing the exact same event ID) are caught by database primary key uniqueness constraints and fail atomic insertion, preventing duplicate user timeline logging.

### 4. Fault Isolation & Error Boundaries
- Subscribers are completely isolated from one another.
- If a subscriber throws an exception (synchronous or async via a rejected Promise), the Event Bus catches and logs the failure to console/telemetry, continuing to propagate the event to all other healthy subscribers.
- Errors in a subscriber (such as a database lock in the Persistence Subscriber) do not block other subscribers (like Timeline updates) from executing or stall the main thread.

### 5. High-Throughput performance
- Benchmark benchmarks verify sub-millisecond execution times.
- Throughput target: > 10,000 events/sec under standard SQLite transactions.
- Memory growth: must remain flat during sustained high-volume publishing.

## Consequences
- **System Stability**: Subsystem crashes are isolated, preventing one faulty subscriber from bringing down the entire companion platform.
- **Data Integrity**: Append-only design prevents event modification, ensuring that historical records remain pristine.
- **Performance**: High-volume benchmarks demonstrate that the system scales efficiently under sustained stress.
